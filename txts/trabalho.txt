2.5 SEE-U-L4TER: Uma Cápsula do Tempo Criptográfica

O objetivo deste trabalho é desenvolver um sistema que permita cifrar mensagens ou ficheiros de forma a que apenas possam ser decifrados numa data e hora previamente definidas.

Para garantir maior segurança, o sistema deve seguir uma arquitetura cliente-servidor, por exemplo sob a forma de uma aplicação web, em que o componente do servidor esteja claramente separado do cliente. O servidor será responsável pelas operações sensíveis, nomeadamente pela geração de chaves de cifra para instantes temporais específicos e pela cifra de ficheiros com essas chaves.

O sistema deve disponibilizar três grandes funcionalidades, que podem eventualmente surgir em três interfaces distintas:

1. Cifra de ficheiros para abertura futura
Um utilizador deve poder submeter um ficheiro e indicar uma data e hora específicas em que esse ficheiro poderá ser aberto, por exemplo: 25 de maio de 2030 às 12h00.
O sistema deverá então:
- gerar uma chave AES única;
- fazer essa chave depender de um segredo interno do sistema, do e-mail do utilizador que submete o ficheiro e da data e hora indicadas;
- cifrar o ficheiro com essa chave;
- devolver ao utilizador apenas o criptograma, sem revelar a chave de cifra.

Depois disso, o utilizador poderá guardar ou enviar o criptograma a qualquer outra pessoa.

2. Divulgação da chave correspondente ao momento atual
Qualquer utilizador deve poder aceder ao sistema e consultar, através de uma interface não autenticada, a chave correspondente à data e hora atual.
Ou seja, o sistema poderá divulgar chaves de decifra em cada momento, mas cada chave só estará disponível no respetivo período temporal, nunca antes nem depois.

3. Decifra de ficheiros cifrados
Opcionalmente, o sistema poderá também disponibilizar uma interface onde o utilizador submete:
- uma chave de cifra;
- um ficheiro anteriormente cifrado.

Se a chave estiver correta e a operação for bem sucedida, o sistema devolve o ficheiro decifrado.

Funcionalidades básicas obrigatórias

O sistema deve suportar, no mínimo, as seguintes operações:

1. Geração de chaves para o momento atual
O sistema deve gerar chaves de cifra pseudoaleatórias usando um algoritmo criptográfico e mostrá-las numa interface isolada para a data e hora atuais, por exemplo na landing page.
As chaves devem depender de:
- um e-mail;
- um segredo conhecido apenas pelo sistema;
- o dia e a hora atuais.

Exemplo:
SHA256(email || segredo || data_hora)

2. Geração de chave e cifra de ficheiros para um instante futuro
A pedido de um utilizador, o sistema deve gerar uma chave para uma data e hora especificadas, usando a mesma técnica, e cifrar com essa chave um ficheiro submetido pelo utilizador.

3. Geração de código de autenticação
Durante a operação anterior, o sistema deve também gerar um código de autenticação de mensagem do tipo HMAC-SHA256, que será anexado ao criptograma.

4. Decifra mediante chave fornecida
A pedido de um utilizador, o sistema deve tentar decifrar um criptograma submetido, usando a chave que o próprio utilizador fornecer.

5. Verificação de integridade
Durante a operação de decifra, o sistema deve verificar o código de autenticação de mensagem.
Se o código não for válido, o utilizador deve ser avisado de que a integridade do conteúdo não foi confirmada.

Funcionalidades adicionais recomendadas

Para reforçar o trabalho e demonstrar maior domínio técnico, poderão ainda ser implementadas as seguintes extensões:

1. Escolha do modo de cifra
Permitir ao utilizador escolher entre:
- AES-128-CBC
- AES-128-CTR

2. Escolha da função HMAC
Permitir ao utilizador escolher entre:
- HMAC-SHA256
- HMAC-SHA512

3. Assinaturas digitais RSA
Para além da verificação com HMAC, o sistema pode também usar assinaturas digitais RSA.
Nesse caso, o sistema deverá ser capaz de gerar um par de chaves RSA ou utilizar um par previamente instalado pelo administrador.

4. Registo de utilizadores
Permitir o registo simples de utilizadores através de:
- e-mail;
- palavra-passe.

A palavra-passe deverá ser armazenada de forma segura na base de dados, recorrendo a uma representação apropriada, como hash com salt.

5. Acesso a chaves passadas
Caso exista sistema de autenticação, os utilizadores registados poderão consultar qualquer chave de cifra do passado, mas nunca chaves futuras.

6. Outras extensões
Podem ainda ser acrescentadas outras funcionalidades consideradas relevantes ou interessantes para enriquecer o projeto.

Aspeto importante para a apresentação

Deve também ser pensada uma possível forma de atacar o sistema, explorando uma falha de implementação ou de desenho.
Esse cenário de ataque deve ser preparado e apresentado brevemente durante a apresentação final do trabalho.

Nota final

Para efeitos de avaliação e prototipagem, o sistema pode executar localmente todos os seus componentes, desde que simule ou concretize a arquitetura cliente-servidor sugerida.
Ou seja, não é obrigatório que o sistema funcione efetivamente em rede, desde que a separação lógica entre cliente e servidor esteja representada.

3. Como "prender" a chave ao tempo
Opção A: (mais simples e prática)
-o servidor gera uma chave aleatória
-cifra o ficheiro com essa chave
-guarda a chave no servidor
-só entrega a chave ou decifra o ficheiro quando chegar a data/hora

Opção B: (mais criptográfica) (mais interessante teoricamente e mais valioso para o professor)
-a chave é derivada de informação temporal 
-ou existe um mecanismo de libertação de chave só num certo momento

CUIDADOS A TER 
1. Não confiar na hora do utiliador
O utilizador pode mudar a hora da sua máquina.
Por isso, usar sempre a hora do servidor. 

2. Não guardar a chave de forma absurda
Se a chave estiver exposta no cliente ou num ficheiro sem qualquer proteção, o sistema perde valor. 

3.Pensar no que significa "só pode ser aberto" (uma boa coisa para referir no relatório) 
Na prática, se o servidor já tiver a chave e alguém compromemter o servidor, pode obter aceeso antes do tempo. 
Ou seja, há uma diferença entre: 
-bloqueio lógico 
-garantia criptográfica forte

9. Como tratar a data/hora

Importante

Pelo texto, parece mais consistente usar hora exata como unidade principal, por exemplo:
	- 2026-03-14 18:00
	- 2030-05-25 12:00

Assim a chave muda de hora a hora.
Isso também encaixa melhor na funcionalidade “mostrar a chave do momento atual”.



10. Derivação das chaves


Entrada
	-email normalizado em lowercase
	-segredo interno do sistema
	-timestamp normalizado

Vantagens
	-simples
	-previsível
	-fácil de explicar

11. Processo completo de cifra

Fluxo
	1.utilizador envia email + data/hora + ficheiro
	2.servidor normaliza timestamp
	3.servidor deriva aes_key
	4.servidor deriva hmac_key
	5.servidor gera IV/nonce aleatório
	6.servidor cifra ficheiro
	7.servidor calcula HMAC
	8.servidor devolve ficheiro .json ou .seelater



12. Processo completo de decifra

Fluxo
	1.utilizador submete chave + ficheiro cifrado
	2.servidor lê metadados
	3.servidor recalcula/verifica HMAC
	4.se HMAC falhar:
		-avisa que a integridade não foi confirmada
	5.se HMAC passar:
		-tenta decifrar com a chave dada
	6.se a chave estiver correta:
		-devolve ficheiro original
	7.se não:
		-devolve erro de decifra

16. Ataque para a apresentação

O enunciado pede que penses numa forma de atacar o sistema  

Uma ideia muito boa e fácil de explicar:

Ataque por falha de desenho: reutilização da mesma chave para cifra e HMAC

Se o sistema usar mal o material criptográfico, pode introduzir fragilidades.

Mas ainda melhor para apresentação:

Ataque por manipulação sem verificação de integridade

Se alguém alterar o criptograma e o sistema tentar decifrar sem validar HMAC primeiro:
	-pode aceitar dados corrompidos
	-pode devolver lixo
	-pode abrir portas a ataques

Demonstração prática
	-cifras um ficheiro
	-alteras 1 byte no campo ciphertext
	-tentas decifrar
	-mostras que:
		-sem HMAC bem implementado, o sistema podia aceitar
		-com HMAC, o sistema deteta alteração


Outra hipótese:

Ataque se o segredo do sistema estiver hardcoded e exposto

Se o atacante obtiver o segredo interno:
	-consegue derivar chaves futuras
	-quebra a ideia de cápsula do tempo



17. Cuidados de implementação

Não fazer:
	-usar hora do cliente em vez da do servidor
	-guardar segredo no código fonte público
	-usar a mesma chave sem separação para tudo
	-tentar decifrar antes de validar integridade
	-aceitar qualquer formato de data sem normalização

Faz isto
	•	segredo em .env
	•	timestamp normalizado
	•	chaves separadas para AES e HMAC
	•	HMAC verificado antes da decifra
	•	mensagens de erro claras
